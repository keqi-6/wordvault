## 五、**未完成**（按优先级）

### 1. 【最高】问题 1：关系跳转后选中词偏右 12%

**现象**（用户录屏实测）：同一层级，正常时偏 −0.7%~+1.4%，**某些操作后跳到 +12%**。

**复现序列**（1570×758 窗口）：
1. 干净 L0，等 HUD 出现 `星点 全库 26608`
2. 搜索 `biological` → 选中 → 读 HUD 的 `选中词 x…（偏 …%）`（应 ≈0）
3. 在**画布上**点它的联系词 `biology`（不是点右侧面板的 chip）
4. 等 10 秒 → 再读 `选中词偏 x`：**当前会变成 +12%**

**已定位的机制（候选 a，最可能）**：
点击画布上的联系星会经过 OrbitCam 的 pointer 处理，`cam.lastUserInput()` 被更新；
而 `ctx.selectedAt` 是在随后的 focus effect 里才写 → `lastUserInput() > selectedAt`（差几毫秒）
→ "用户没动过相机"这个前提不成立 → **自动对齐被永久跳过** → 相机停在 `flyToStar` 的取景上。

**修法**：把"用户干预"的判据从"任何 pointer 事件"改成**只有真实拖拽（位移 > 6px 且持续 > 2 帧）或滚轮才算**；
并考虑把 `selectedAt` 改到**点击那一刻**写，从根上消掉毫秒级竞争。

**A/B 判据（先做这个再改）**：
同一步分别用「画布点联系星」与「右侧面板点 chip」，
- 若画布 +12% / 面板 ≈0% → 确证候选 (a)
- 若两条都偏 → 是候选 (b)：取景里的"团心约束"过大

**验收**：两条路径**都必须 < 5%**；且**必须复测拖拽保护不退化**（那条之前是 0.00%）。

## 六、验收方法论（**这部分比代码更重要**）

### 三个"失败时会直接变红"的硬指标

| 指标 | 含义 | 期望 |
|---|---|---|
| `已移动 N` | 当前被拉离原位的星数（HUD） | 无选中时 = 0；选中时 = 联系词数 |
| `连线 N（在框内 M）` | 端点用真实相机投影后落在画布内的个数 | N == M |
| `实亮 / 本级` | vis ≥ 0.5 的星点数 ÷ 本级词数 | ≈ 100% |

外加观感用的结构量：`亮度>40 占比`（防糊）、`四角 RGB`（防变黑）、`取景 r`（防相机过远）。

### 幂等性验收（**动态残留的天敌**）

> **不管用什么路径到达同一个状态，结果必须一致。**

- "直接搜 C" vs "A→B→C 点过来"
- "选中 A → 取消 → 再选 A" vs "直接选 A"
- "切换星相再切回" vs "一开始就是那套星相"

### 我犯过的五个坏指标（**别再犯**）

| 坏指标 | 它测不到什么 |
|---|---|
| 亮度>40 占比（当目标用时） | 把画面调成全黑也"达标" |
| 星团中位半径 | 团与团是否重叠 |
| 微光像素总量 | 是星团撑大的还是连线撑大的 |
| 整幅光重心 | 用户到底在看哪个东西 |
| 平均亮度 | 背景有多黑 与 星云有多亮 是两个来源，被混在一个数里 |

**共同点：它们都能在画面变差时显示得"更好看"。**
**原则：数字只守底线（别糊/别黑/别漏/别部分更新），观感一律看图。**

### 三条抓 bug 的有效手段

1. **看录屏抽帧** —— 单帧闪烁和"突然跳变"只有录屏能抓到；我的无头环境（1–15fps）物理上抓不到单帧现象；
2. **在慢 50 倍的环境里复测** —— 只有软件渲染（`--disable-gpu --use-angle=swiftshader`）能暴露时序依赖；
3. **让程序自报状态** —— HUD 里的 `取景 r` `已移动 N` `贴图 N` `选中词偏 x%` `面板 W` `窗口 W` 都是为此加的。

### 11.2 已做的修复

**① 音标规范化**（`common.py: normalize_phonetic`）
字符映射表是**从实际字符统计 + 抽样验证**得出的，不是猜的：

```
ә(U+04D9) → ə     ^ → ɡ（损坏的 g）   反斜杠 → ɜ（损坏的 ɜ）
: → ː（长音符）   ' → ˈ（主重音）      . → ˌ（次重音）
є(U+0454)/ε(U+03B5) → ɛ             (?@) → ；
双元音: ai→aɪ  ei→eɪ  au→aʊ  əu→əʊ  ɔi→ɔɪ
```
效果：西里尔 0、ASCII 撇号 0、标准重音 836→20,471、标准长音符 50→6,671。

**② 义项去重**（`build_db.py: dedupe_senses`）
归一化后完全相同 → 保留先出现的；一条被另一条包含 → 保留更完整的。61,328 → 50,604。

**③ 词根修正**（`build_db.py: clean_root`）
`root` 去掉等于词本身的成分。7,642 → 0。

**④ 例句清洗**（`build_db.py: clean_example`）
去掉结尾题号与开头选项标记。1,294 → 86（剩下的多是有意义的数字）。

**⑤ Tatoeba 中英对照**（新模块 `tatoeba_zh.py`）
⚠️ **两个坑（都值得记住）**：
1. **`links.csv` 是通用翻译链接、不区分语言** —— 早先把"任何出边的翻译"都当成中文配对，
   筛出来只剩 3%。必须先读全部中文句 id（89,102 条），再筛 links；
2. **"先筛句子再找配对"是错的结构** —— 没有配对的句子会占满候选池（上限 150 万），
   正确做法是**先挑出有中文配对的句子（62,835 条），再按词索引**。

结果：人工中英对照例句 1,826 → **18,728**；六级词有中英对照 **68.6%**。

**⑥ 繁简转换**（`tatoeba_zh.py: to_simplified`）
Tatoeba 中文语料**繁简混杂**，装了 `opencc-python-reimplemented`（清华镜像）做 t2s。
抽样 4,000 条，繁体残留 0%。

**⑦ 机器翻译补缺**（`scripts/pipeline/translate_examples.py`）
线上服务探测结果：**Google / Bing / 有道 / 百度 / LibreTranslate 全部不可达**，
**只有 MyMemory 可用**（`https://api.mymemory.translated.net/get`）。

⚠️ 三条实测经验：
- **不能并发** —— 开 6 个线程立刻被 HTTP 429 拒；必须串行；
- **连接复用是提速关键** —— 串行时单条 4.8s，其中大半是重复 TLS 握手，
  复用 keep-alive 后降到 2s；
- **额度按邮箱发放、按小时重置** —— 匿名约 5,000 词/小时，带 `de=<email>` 是 50,000 词/小时。
  提示语是 `NEXT AVAILABLE IN 00 HOURS 34 MINUTES`。

脚本支持 `--email` `--delay` `--auto-wait`（额度用尽自动等 40 分钟再继续）。
机器译文写 `is_machine=1`，与人工译文（Tatoeba）区分。**每 25 条提交，可断点续跑。**

